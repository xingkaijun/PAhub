# PAhub 设计说明（v0.5，2026-11-08）

PAhub = D1-PAPC（图纸审批进度）+ PG PCF v1.9（每张图一份意见记录表），部署在局域网 Ubuntu 服务器，供审图小组使用。

## 已确定的决策
1. 意见正文、图片、往来记录**只存在 PCF 文件里**，数据库不存正文。
2. 数据库只存 PCF 指针和摘要：drawingId、documentId、文件路径、意见总数、未关闭数、当前轮次、PCF 版本号、最后更新时间。
3. 每张图一个 PCF 文件；意见往来通过邮件发送/接收 PCF 文件。
4. 发给船厂的 PCF **锁定 Owner 栏**，船厂只能填写导出时当前轮次、未关闭意见的 Builder 回复和附图；回复日期/编号等轮次登记也只读。
5. 在线编辑为**匿名**（不需要登录）。
7. **内部 JSON、离线/往来 HTML**（架构优化阶段 2 修订）：服务器每张图的权威数据存为 JSON，历史快照也为 JSON；模板保持独立单文件 HTML，启动时读入内存，页面由模板 + 数据 + `pahub-context` 渲染。完整离线副本、发给船厂的外发版及收到的回复仍为单文件 HTML。数据库仍不存正文（决策 1、2 不变）。
6. 服务器：Ubuntu，局域网 http 访问。浏览器的 File System Access API 在非 HTTPS 下不可用，因此在线模式由服务器负责保存。

## 架构
- 一个 Node 24 进程（`hub-server/`）：
  - 托管 PAPC 前端（vite build 产物）。
  - 在 `/api/*` 提供 PAPC 原有 API：图纸/项目、review-tracker、audit/heartbeat、settings/health、admin 已迁入 hub-server 原生模块。统一路由与中间件负责 JSON、错误、日志、可选鉴权；读接口直接查规范化表，写入代码提交后直接发出通知。
  - SQLite 数据库文件：`data/papc.db`。
  - PCF 文件：`data/pcf/<projectId>/<drawingId>.json`，JSON 是权威数据（含实体时钟和幂等回执）。历史版本：`data/pcf/<projectId>/.history/<drawingId>/<rev>-<时间>-<uuid>.json`。使用稳定 drawingId，不用可改名且可能含非法字符的图号；数据根目录由 PAHUB_DATA_DIR 配置。
  - PCF 页面：`/pcf/<projectId>/<drawingId>` 用当前内存模板和权威 JSON 渲染，注入仅供在线页面使用的上下文；托管保存直接原子写 JSON。开发模式模板修改后重新加载，生产升级模板只需替换模板并重启，不再批量重写文档。
  - 外发版仍按白名单重建独立 HTML（船厂版锁定 Owner 和控制字段）；完整离线副本仅移除 Hub 内部时钟/回执/clientId/IP，保留流转、审批及删除记录。两种副本均记录导出基线，导回按基线/离线副本/服务器现状三方合并，不整份覆盖。往来基线和收到的原始回复仍存 HTML。
  - 数据库 schema 使用编号 SQL 和 `PRAGMA user_version`：001 为现有完整结构，002 仅由停服迁移脚本在 JSON 校验和安装完成后记录。启动不自动转换 PCF。
- 部署：systemd 服务（或 Docker），一个端口，定时备份 `data/`。

## 在线编辑与多人冲突处理（匿名）
目标：多人同时编辑同一张图时，不丢数据、不互相覆盖，冲突粒度尽量小。

1. **身份**：匿名，但每个浏览器生成一个持久的 clientId（localStorage），可选填写昵称（默认“Editor-xxxx”）。服务器在变更日志里记录 clientId、昵称、IP、时间，便于追溯。
2. **按操作保存，不整文件覆盖**：PCF 托管模式下，客户端发送的是细粒度操作（ops），例如：
   - `comment.add`（编号由服务器分配，避免两人建出同号意见）
   - `round.add`、`content.update`（某意见某轮的 owner 或 reply 内容）、`comment.status`、`comment.meta`（页码、标签）、`project.update`（图纸信息字段）、`roundRegister.update`、`delete/restore`
   每个 op 带上它修改的那个实体（某轮的 owner/reply、某条意见的状态……）的 `baseRev`。
3. **服务器串行化**：每张图一个内存互斥锁；按顺序把 ops 应用到最新 JSON，原子写盘（写临时文件后 rename），文档 rev +1，保存历史版本，重算摘要写回数据库。
4. **冲突判定**：只有当同一个实体在 `baseRev` 之后被别人改过，才算冲突；不同意见、同一意见不同轮次、同一轮次 owner 与 reply 之间互不冲突，自动合并。冲突的 op 不应用，返回双方内容；客户端弹出对比，让编辑者选“用我的 / 用对方的 / 手动合并后再提交”。
5. **实时感知**：每张图一个 SSE 通道。
   - 推送别人已保存的变更，页面就地刷新对应意见（正在编辑的那一格不被打断，只提示“已被他人更新”）。
   - 在线状态：显示当前有几人在看这张图；某人光标进入某条意见的编辑区时广播“某某正在编辑 #5”，其他人看到该格的软锁提示（不强制，60 秒无活动自动释放）。
6. **离线兜底**：网络断开时 ops 暂存本地队列，恢复后按顺序重放，冲突走第 4 条。
7. **撤销与追溯**：所有历史版本可在页面查看并恢复（恢复本身也是一个新版本）。

## 邮件往来
1. **导出发出**：图纸行“导出 PCF”→ 生成独立离线 HTML（模板 + 当前数据，`mode: "builder"`，Owner 栏只读），服务器同时把该时刻数据存为“发出基线”（记录 rev 和导出时间）。
2. 船厂离线打开、填写 Builder 回复，另存后邮件发回。
3. **导入回复**：在该图点“导入回复”上传文件 → 校验 documentId 一致 → 三方合并（基线 / 服务器当前 / 船厂版）：
   - Owner 栏锁定，只合并导出当前轮次的 Builder reply（正文/格式、整体附图集）；replyDate/replyRef 也属于只读登记，不从返回文件导入；
   - 若船厂版的 Owner 内容与基线不同（绕过锁定），不自动并入，单独列出提示；
   - 我方在基线之后也改了同一条 reply 的，列为冲突逐条选择；
   - 船厂新增/删除意见一律不导入；服务器导出后新增意见保留，服务器删除且船厂新增回复时列为恢复冲突。
   - 合并前自动备份，预览确认后写入；合并本身作为一组 ops 走同一条串行通道，与在线编辑互不覆盖。

## 职责划分
- PAPC：图纸状态、负责人、期限、送审/回复日期；APR 仅为 tracker 中的手动标记，Send All 只按该标记选择 Approved / Waiting Reply。
- PCF：意见内容、开闭、每条意见的轮次及独立的认可状态；认可状态不回写 PAPC。
- 意见总数、未关闭数、当前轮次：由 PCF 自动回写 PAPC，取代手工 `c:10/2`。
- 轮次登记以 PCF 为准；每次写入回写 PAPC 当前轮次（PCF 数字 1/2/3 ↔ PAPC A/B/C）及当前轮次的非空 revision，同时更新意见总数/未关闭数。轮次登记编号和日期保存在 PCF JSON 及 pcf_index.rounds_json 摘要中，本期不转换为 PAPC 送审/回复日期。审计使用现有 COMMENTS 类型，兼容现有报表；完整协议见 [PCF_HOSTED.md](PCF_HOSTED.md)。
